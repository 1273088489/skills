# Team Orchestration

Captain 把一个大目标推进到“可交给用户审核的未提交改动”的 watch loop：拆解、派发、监督、唤醒、验证。目标是过程可重复，不是让每个子对话一次成功。

## 1. 先固定目标与边界

- 读仓库现状、既有规格、已有大纲，确认“要完成什么”而不是从零猜。
- 写一份最小大纲/规格：用户可见目标、每个任务的验收、禁止动作。
- 禁止动作至少包含：不提交、不合并、不推送、不改依赖、不擅自新增后端路由。

**完成标准**：每个任务都有独立负责人和可检查的产出路径，且范围和禁止动作写在可派发材料里。

## 2. 创建团队并按任务拆分子对话

- 每个大纲任务对应一个独立子对话/成员，不要给同一个成员堆多个大任务。
- 按文件所有权拆分，避免并行子对话改同一文件；必要时取消原任务并新建任务改派。
- 成员角色可从角色目录读取，例如 agency-agents；没有可用角色时按职责命名，不虚构。

**完成标准**：任务集合能并行、路径不重叠、每项都有验收或验证方式。

## 3. 用 task packet 派发

每个子对话消息必须自包含，不依赖主对话的历史：

- 工作目录和允许修改的文件。
- 接口契约、现有 API、数据形状。
- 验收标准、最小可运行范围、验证命令。
- 禁止动作：不提交、不合并、不改 package.json。
- 完成时报告格式：改动文件、实现要点、验证结果、遗留风险。

**完成标准**：成员只凭 task packet 即可开始工作，且不重复主对话未给的信息。

## 4. 进入 watch loop：监督、唤醒、验证

- 认领任务并标记 in_progress，发 task packet 唤醒成员。
- 定期检查成员 activity、任务 output、git status；任何“运行中但长时间无产出”都是待唤醒信号，不必等失败通知。
- 唤醒：中断疑似卡住的回合，重新发一个更小的 task packet（单文件、最小可运行范围），不要重复原长指令。
- 同一成员连续失败时，先缩小任务；仍不行再改派，但保持“每个大纲任务仍在独立子对话完成”。
- 以 git diff 为准，不信任口头“已完成”；任务输出与文件不一致时要求成员补产出。

**完成标准**：没有任务留在 in_progress 且无人认领；每个任务都有 completed 状态、产出文件或明确报告。

## 5. 汇总、验证、审查、留审

- 逐个检查 diff：数据契约、SSR/客户端安全、未授权改动、package.json、新增路由。
- 跑 typecheck、test、build；必要时跑 diff --check。
- 派最终审查子对话；严重问题先修复再复验，一般问题记录为可选优化。
- 保持所有改动未提交，输出审核清单：改动文件、验证结果、剩余建议、未提交声明。

**完成标准**：验证全绿，最终审查已记录，改动未提交/未合并/未推送，等待用户审核。

## 关键失败信号

- 成员失败或关闭且无报告：唤醒并补发最小 task packet。
- 成员显示 running 但多次检查无文件产出：中断后重新派发，缩小范围。
- 任务输出与 git 状态不一致：以 git diff 为准，要求成员补产出。
